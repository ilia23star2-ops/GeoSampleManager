# Правила работы ИИ над GeoSample Manager

> **ЧИТАЙ ПЕРВЫМ.** Этот файл описывает, как ИИ должен отвечать, форматировать
> код, что запрашивать у пользователя и куда смотреть за контекстом.
>
> Соблюдение обязательно. Единый формат — чтобы при смене чата новый ИИ
> сразу понял правила и продолжил работу без переобъяснений.

**Репозиторий:** https://github.com/ilia23star2-ops/GeoSampleManager

## 1. Стиль общения

- **Язык — русский.** Комментарии в коде — русские. UI — русский.
- **Без воды.** Не повторяй, что сказал пользователь. Не пиши «отличный
  вопрос» и «давайте разберёмся».
- **Коротко и по делу.** Абзацы — 2–4 строки. Списки — там, где они уместны.
- **Уважительно и по-рабочему.** Пользователь — разработчик, не нуждается в
  разжёвывании очевидного.
- **Не извиняйся без причины.** Ошибся — исправил, коротко отметил.
- **Не спрашивай разрешения на очевидное.** Если нужно уточнить — задай
  конкретный вопрос с вариантами А/Б/В.

## 4. Правила кода

### 4.1. Стиль
- **Kotlin, Jetpack Compose, Room.**
- **Комментарии — на русском.**
- **Имена классов, функций, переменных — английские.** Примеры:
  `PhotoStorage`, `ReconciliationState`, `voiceSettings`.
- **Отступ — 4 пробела.**
- **Максимум 100 символов в строке**, если возможно.

### 4.2. Структура
- Пакеты — `com.example.geosamplemanager.<слой>`.
- `data/`, `data/entity/`, `data/dao/`, `data/util/`, `data/voice/` (план).
- `ui/screens/`, `ui/navigation/`, `ui/theme/`.
- Никаких файлов «всё в одном». Разделяй по ответственности.

### 4.3. Работа с БД
- **Все изменения схемы — только через миграции.**
- Перед созданием / изменением сущности — сверить с `DATABASE.md`.
- После изменения — **предупредить** пользователя и обновить `DATABASE.md`.
- **Никогда не удалять колонку без миграции.**

### 4.4. Асинхронность
- **Все I/O — в `Dispatchers.IO`.**
- Обновление UI-состояния — через `withContext(Dispatchers.Main)`.
- Долгие операции — не в главном потоке.

### 4.5. Работа с файлами
- **Фото — только в `filesDir/sample_photos/`.**
- **Файлы БД — только в `getDatabasePath()`.**
- **Настройки — в `filesDir/*.json`.**

### 4.6. Обработка ошибок
- **Ловить исключения в каждом I/O-блоке.**
- Сообщение об ошибке — в `_message.value`.
- Никогда не «глотать» ошибки молча.

## 5. Формат раздела «Как проверить»

После каждого захода **обязателен** раздел:
✅ Как проверить заход X.Y
1. Сборка
Что нажать, что должно быть.

2. Запуск
Что должно открыться.

3. <Сценарий 1>
Пошаговые действия.

Ожидаемое поведение.

4. <Сценарий 2>
...

5. Если что-то падает
Куда смотреть, что прислать.

text

**Правила:**
- **Конкретные действия:** «нажми молоток», «открой меню», «введи 1524».
- **Конкретные ожидания:** «должно появиться…», «снекбар: "Заметка
  сохранена"».
- **Простой язык.** Не «проверить в Logcat тег Room», а «приложение
  запускается без ошибок».
- **Если критично — без adb и SQL.** Пользователь — не разработчик ядра.

## 6. Что делать при ошибках

### 6.1. Сборка упала
- Попросить **полный текст ошибки** (не скриншот, а текст).
- Найти причину, исправить, выдать **полный файл** заново.

### 6.2. Логика не работает
- Попросить **что именно происходит** vs **что ожидалось**.
- Не угадывать. Уточнить:
    - Что нажал?
    - Что увидел?
    - Что было в логах?

### 6.3. Миграция БД упала
- Сказать пользователю снести приложение и запустить заново (данных
  рабочих нет).
- Исправить `Migration`.
- Выдать полный файл.

## 7. Правила по документации

### 7.1. Когда обновлять
- **После каждого закрытого захода** — обновить `PROGRESS.md`,
  `NEXT_STEPS.md`, при необходимости `ROADMAP.md` и `DECISIONS.md`.
- **Решения по ходу** — в `DECISIONS.md`.
- **Изменения БД** — в `DATABASE.md`.

### 7.2. Как обновлять
- **Файл целиком**, не фрагмент.
- **Пометка «Заменить полностью»** — жирным.
- **Путь в текстовом блоке.**
- **Шапка `X/Y`** — как у кода (см. §2).
- **Раздел «Как проверить»** — не нужен для документации, но можно
  попросить пользователя пролистать.

### 7.3. Напоминание про репозиторий

**После каждого закрытого захода**, когда код прошёл и документация
обновлена, добавь **в самом конце ответа** напоминание:
Заход X.Y закрыт. Файлы можно пушить:

Репозиторий: https://github.com/ilia23star2-ops/GeoSampleManager

Коммит: 5.8.3 — префиксы + поиск (или актуальный номер захода).

text

Пользователь пушит вручную с подписью номера захода. Дай ему готовую
строку для коммита — это экономит время.

**Формат строки коммита:** `<номер захода> — <краткое описание>`.
Примеры:
- `5.8.3 — префиксы + поиск`
- `5.11 — множественный поиск UI`
- `5.8.2 — парсер ГП`

## 8. Принципы обсуждения

### 8.1. Перед кодом — обсуждение
Если задача сложная (новая архитектура, много конфликтов):
1. **Сначала спецификация** — что делаем, какие правила, какие конфликты.
2. **Проверка на конфликты** — пользователь отвечает, ИИ уточняет.
3. **Фиксация** — обновляем документ (например, `VOICE.md`).
4. **Только потом код.**

### 8.2. Не пиши код, если:
- Нет полного понимания задачи.
- Пользователь задал вопрос «как лучше?».
- Есть открытые вопросы, влияющие на архитектуру.

### 8.3. Аудит
Перед реализацией крупного блока — **аудит**:
- Каталог команд / функций.
- Проверка на конфликты.
- Открытые вопросы.
- Список проблем.

Только после ответов пользователя — код.

## 9. Приоритеты

1. **Работающий код > красивый код.** Не оптимизируй преждевременно.
2. **Простое решение > сложное.** Если можно сделать без библиотеки —
   сделай без.
3. **Понятный код > лаконичный.** Пользователю важно читать, не
   разгадывать.
4. **Документация > код без документации.** Будущий ИИ должен понять
   контекст без тебя.

---

## 10. Что категорически нельзя

- **Обрезать код** («…», «остальное как было»). Всегда целиком.
- **Угадывать** содержимое файлов, которые пользователь не присылал.
- **Менять схему БД** без предупреждения и миграции.
- **Использовать Apache POI.** Проект его избегает.
- **Писать комментарии на английском.** Только русский.
- **Забывать раздел «Как проверить».**
- **Отвечать без номера файла** («вот файл:» без пути).
- **Давать фрагменты пути.** Только полный путь от корня проекта.
- **Забывать шапку `X/Y`.** Даже для одного файла пиши `1/1`.
- **Забывать ссылку на репозиторий** в конце закрытого захода (см. §7.3).

## 16. Финальное правило

**Пользователь — не робот.** Он устаёт, отвлекается, ошибается.
Твоя задача — **сокращать его работу**, а не добавлять.

Каждый твой ответ должен:
- Не заставлять переспрашивать.
- Не заставлять копировать по частям.
- Не заставлять догадываться, что проверять.
- Экономить его время.

Если сомневаешься между «сделать быстро» и «сделать понятно» —
**делай понятно**.

## 17. Стоп-сигналы — когда ИИ обязан остановиться

**Если задача попадает хотя бы в один пункт — ИИ не пишет код.
Сначала спрашивает.**

1. **Задача затрагивает >3 файлов.** Спросить: «Разбить на части?».
2. **Задача меняет схему БД.** Спросить: «Какая миграция?».
3. **Задача меняет публичную сигнатуру** (класс, DAO, ViewModel API).
   Спросить: «Кто ещё это использует?».
4. **Задача противоречит `CONTEXT_BRIEF.md`.** Сказать прямо.
5. **Задача сформулирована словами** «улучшить», «оптимизировать»,
   «починить», «отрефакторить». Спросить: «Что конкретно?».
6. **Нужно удалить код** из проекта. Спросить подтверждение.
7. **Правка каскадит** — тянет за собой ещё 2+ файла. Остановиться,
   сообщить, ждать решения.
8. **Задача похожа на уже сделанную раньше.** Спросить: «Повторяем или
   изменяем?».
9. **В чате >30 сообщений.** Предложить обновить `CONTEXT_BRIEF.md`
   и начать новый чат.
10. **Не понятно, что именно надо.** Задать уточняющий вопрос.

## 18. Атомарность заходов

**Правило:** один заход — **1–3 файла**.

- Если файлов больше 3 — задача слишком большая. **Разбить.**
- Если один файл >500 строк — **разбить на классы**.
- Если заход смешивает UI и БД — **разбить**.
- Если заход меняет БД + миграцию + UI — **разбить на 2 захода**:
  сначала миграция + репозиторий, потом UI.

**Почему:**
- Меньше файлов = меньше шансов потерять нить.
- Легко откатить.
- Легко проверить.

**Если задача «на 5 файлов» пришла — не делать сразу.** Сказать:
«Разобьём на два захода: сначала A, потом B. Начинаем с A?».

## 19. Откат по умолчанию

**Если после правки что-то сломалось, и решение неочевидно —
откатить, не чинить.**

### Как

1. Перед заходом — сделать коммит: `git add . && git commit -m "before 5.8.5"`.
2. Если после правки заход не работает — `git reset --hard HEAD`.
3. Вернуться к обсуждению.

### Почему

ИИ, пытаясь «починить поломку», часто ломает ещё больше. Каскад.
Откат — самый быстрый путь вернуться к рабочему состоянию.

### Что НЕ считается поломкой

- Мелкая ошибка в одной строке — исправляется на месте.
- Опечатка в комментарии — исправляется на месте.
- Отсутствующая зависимость в gradle — добавляется.

Поломка — это когда:
- Приложение не запускается.
- Сценарий, который работал, перестал работать.
- БД падает при миграции.
- В логах новая ошибка, которой не было.
