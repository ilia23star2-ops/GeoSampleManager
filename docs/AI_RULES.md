> **ЧИТАЙ ПЕРВЫМ.** Этот файл описывает, как ИИ должен отвечать, форматировать
> код, что запрашивать у пользователя и куда смотреть за контекстом.

## 1. Стиль общения

### 1.1. Общие правила

- **Язык — русский.** Комментарии в коде — русские. UI — русский.
- **Без воды.** Не повторяй, что сказал пользователь. Не пиши «отличный
  вопрос», «давайте разберёмся».
- **Коротко и по делу.** Абзацы — 2–4 строки.
- **Уважительно и по-рабочему.**
- **Не извиняйся без причины.** Ошибся — исправил, коротко отметил.
- **Не спрашивай разрешения на очевидное.** Если уточняешь — задай
  конкретный вопрос с вариантами А/Б/В.

### 1.2. Комментарии к действиям — разделение

| Тип действия | Комментарий |
|---|---|
| **Замена файла в IDE** | **Не писать.** Пользователь знает: `Ctrl+A` → `Delete` → `Ctrl+V` → `Ctrl+S`. |
| **Сборка / запуск** | **Коротко.** «`Build → Make Project`. Ожидаемо: `BUILD SUCCESSFUL`.» |
| **Git-операции в AS** | **Подробно, пошагово.** Куда нажать, что выбрать, что ожидать. См. §2.4. |
| **Git-операции в Terminal** | **Пошагово.** Одна команда — одно действие. |
| **Что-то новое в интерфейсе** | **Подробно.** |

**Важно (интерфейс AS):**
- **Ветки** — **левый нижний угол** окна AS (название текущей ветки).
- **Commit/Push** — иконка Commit слева (3-я сверху в вертикальной панели).

## 2. Формат ответа на заход кода

### 2.1. Структура ответа — пять частей

1. **Шапка захода** (§2.2).
2. **Файлы кода** — по одному блоку на файл (§2.3).
3. **Файлы тестов** — по одному блоку на файл (§2.3).
4. **Раздел «Что проверить вручную»** (§5).
5. **Напоминание про репозиторий и коммит** (§7.3).

**Структура ответа — с git-шагами по ходу.** Git-подсказки встроены
в шапку — в тех местах, где они логически нужны.

**Важно (§24):** merge/delete — **только после подтверждения
пользователя.** Шаги merge даются **не в общем ответе**, а отдельным
сообщением — когда пользователь написал «норм».

### 2.2. Шапка захода — короткая + git-шаги по ходу

**Формат шапки:**
Файлов кода: N
Файлов тестов: M

Заход / Пачка: X.Y — <краткое название>
Фича: feature/X.Y-xxx ← или «нет (docs → main)»
Режим: AS (Android Studio + git в терминале)

**Дальше — git-шаги.** Подсказки `>` — **только для текущего режима**.

#### Вариант 1 — Режим А (AS), пачка в фичу
🐙 Шаг 1. Создать ветку пачки

Terminal (Alt+F12):
git checkout feature/X.Y-xxx
git pull
git checkout -b fix/X.Y-bundle
git push -u origin fix/X.Y-bundle

📁 Шаг 2. Файлы
<файлы>

✅ Шаг 3. Собрать и прогнать тесты

Ctrl+F9 → BUILD SUCCESSFUL. Alt+F12 → ./gradlew testDebugUnitTest → BUILD SUCCESSFUL.

⏸ Шаг 4. Пауза — ждём «норм» (§24)

После сборки и локальных тестов — **жди**. Пользователь прогоняет
device-check и пишет «норм». Только после этого — merge (отдельным
сообщением).

💾 Шаг 5. Коммит + Push

git add .
git commit -m "X.Y-bundle — <краткое>"
git push

🔀 Шаг 6. Merge в фичу (локально)

git checkout feature/X.Y-xxx
git pull
git merge --no-ff fix/X.Y-bundle -m "Merge fix/X.Y-bundle"
git push

🎉 Шаг 7. Удалить пачку

git branch -d fix/X.Y-bundle
git push origin --delete fix/X.Y-bundle

#### Вариант 2 — Режим А (AS), docs в main
🐙 Шаг 1. Создать ветку от main

git checkout main
git pull
git checkout -b docs/X.Y-<краткое>
git push -u origin docs/X.Y-<краткое>

📁 Шаг 2. Файлы
<файлы>

✅ Шаг 3. Проверить

Для docs — ничего. Для кода — Ctrl+F9 + ./gradlew testDebugUnitTest.

⏸ Шаг 4. Пауза — ждём «норм» (§24).

💾 Шаг 5. Коммит + Push

git add .
git commit -m "docs/X.Y-<краткое> — <описание>"
git push

📤 Шаг 6. PR в main

Через github.com в браузере → New Pull Request → base main → Create.

🎉 Шаг 7. Merge

Merge pull request → Confirm merge → Delete branch.

#### Вариант 3 — Режим Б / В (fallback: github.dev / github.com)
🐙 Шаг 1. Создать ветку пачки

Переключиться на фичу → создать ветку fix/X.Y-bundle.

📁 Шаг 2. Файлы
<файлы>

✅ Шаг 3. Проверить

Сборки нет. Тесты — авто на PR.

⏸ Шаг 4. Пауза — ждём «норм» (§24).

💾 Шаг 5. Коммит

github.dev — один общий коммит.
github.com — по одному на файл: X.Y-bundle/N — ИмяФайла.kt.

📤 Шаг 6. PR в фичу

Compare & pull request → Base: feature/X.Y-xxx → Create.

🎉 Шаг 7. Merge

Merge pull request → Confirm merge → Delete branch.

### 2.3. Формат файла

Каждый файл — отдельным блоком:
X/Y. Заменить полностью или Новый файл — <ИмяФайла.kt>
<комментарий, зачем>

Заменить полностью или Новый файл
полный/путь/к/файлу/ИмяФайла.kt
// полный код файла, без сокращений

**Комментарии в коде — на русском. Код полный, без «…».**

**Для `github.com`** — после каждого файла строка коммита в подсказке:
> ✏️ → Commit changes → `X.Y/N — ИмяФайла.kt`.

### 2.4. Git-операции в ответе — пошагово

Все git-операции — **через Terminal в AS** (`Alt+F12`). Один шаг —
одна команда. Не через интерфейс AS (Commit/Push в AS ломает репо).

**Правило.** Пользователь сам сказал: «Git — только через терминал».

### 2.5. Обязательные элементы

1. **Заголовок `X/Y`** — `X` номер, `Y` всего.
2. **Пометка «Заменить полностью»** или **«Новый файл»** — **жирным**.
3. **Полный путь в текстовом блоке** — от корня проекта.
4. **Полный код** в блоке ` ```kotlin `. **Никаких «…»**.
5. **Раздел «Что проверить вручную»** (§5) — с командами для текущего режима.

### 2.6. Имя ветки

| Тип ветки | Префикс | Пример |
|---|---|---|
| Фича (долгоживущая) | `feature/` | `feature/5.9-full-project` |
| Пачка (ответвление от фичи) | `fix/` | `fix/5.9-db-merge-v2-1` |
| Подзаход | `fix/` | `fix/5.9-db-merge-v2-1`, `-2`, `-3` |
| Docs (в main или фичу) | `docs/` | `docs/5.9-db-merge` |
| Одиночный заход | `fix/` | `fix/5.8.9-infra-2a-ci-sdk` |

**Правила:**
- Одна задача — одна ветка.
- **Пачки — ответвление от фичи**, не от `main`.
- **Пачки мержатся в фичу** (локально).
- **Docs** — в фичу (если описывают состояние фичи) или в `main`
  (если описывают общее). По умолчанию — в фичу.
- **Фича мержится в `main`** — когда вся серия готова.
- После merge **пачки** — удалить.
- После merge **фичи** — **не удалять** (архив, §2.9).

### 2.7. Сообщение коммита

| Режим | Способ коммита | Формат |
|---|---|---|
| AS (дома/на работе) | **Один общий** на пачку | `X.Y-bundle — описание` |
| github.dev | Один общий | `X.Y-bundle — описание` |
| github.com | **По одному на файл** | `X.Y-bundle/N — ИмяФайла` |

**Почему так:** на github.com веб-редактор коммитит только текущий файл.

### 2.8. Пачки (bundles) и подзаходы

**Пачка** — группа связанных заходов в одной ветке с одним device-check.

**Правила пачки:**
- Пачка — **3–7 файлов кода** + тесты.
- Пачка — **одна логическая задача.**
- **Один device-check** на пачку.
- AS — **локальный merge** в фичу.
- Fallback (github.dev/github.com) — **PR в фичу**.

**Подзаходы:**
- **Каждый подзаход = отдельная ветка** `fix/X.Y-bundle-1`,
  `fix/X.Y-bundle-2`, `fix/X.Y-bundle-3`.
- **Свой коммит**, **свой merge в фичу**, **свой «норм»**.
- Так проще откатывать: откат одного подзахода — удаление ветки
  или `git revert`, не трогая остальное.

**Откат:**
- Упал один подзаход — не мержить его ветку в фичу.
- Упала вся пачка (несколько подзаходов) — не мержить оставшиеся.

### 2.9. Жизненный цикл веток
main
│
├── feature/X.Y-xxx ← активная фича (долгоживущая)
│ ├── fix/X.Y-xxx-bundle-1 ← подзаход (живёт до merge)
│ ├── fix/X.Y-xxx-bundle-2
│ └── fix/X.Y-xxx-bundle-3
│
├── feature/X.Y-yyy ← архив (закрыта, НЕ удаляем)
│ └── feature/X.Y-yyy-v2 ← возврат через время
│
└── feature/X.Y-zzz ← архив

**Фича.** Долгоживущая. Не мержится в `main` до готовности всей серии.
**После merge в `main` — НЕ удаляется.** Остаётся как архив.

**Пачка.** Короткая. Живёт до merge в фичу. **После merge — удаляется.**

**Архивная фича.** Закрыта, не удалена. Возврат — новое ответвление
`-v2`, `-v3`.

**`main`.** Трогается редко. Только merge готовой фичи или docs.

## 4. Правила кода

### 4.1. Стиль
- Kotlin, Jetpack Compose, Room.
- Комментарии — на русском.
- Имена классов/функций/переменных — английские.
- Отступ — 4 пробела.
- Максимум 100 символов в строке.

### 4.2. Структура
- Пакеты — `com.example.geosamplemanager.<слой>`.
- `data/`, `data/entity/`, `data/dao/`, `data/util/`, `data/voice/`,
  `data/backup/`, `data/merge/`, `data/compare/`.
- `ui/screens/`, `ui/navigation/`, `ui/theme/`.
- Никаких файлов «всё в одном».

### 4.3. Работа с БД
- Все изменения схемы — только через миграции.
- Перед изменением сущности — сверить с `docs/DATABASE.md`.
- После изменения — предупредить и обновить `docs/DATABASE.md`.

### 4.4. Асинхронность
- Все I/O — в `Dispatchers.IO`.
- Обновление UI — через `withContext(Dispatchers.Main)`.

### 4.5. Работа с файлами
- Фото — `filesDir/sample_photos/`.
- БД — `getDatabasePath()`.
- Настройки — `filesDir/*.json`.
- Бэкапы (приватные) — `filesDir/db_backups/`.

### 4.6. Обработка ошибок
- Ловить исключения в каждом I/O-блоке.
- Сообщение — в `_message.value`.
- Не «глотать» ошибки молча.

## 5. Формат раздела «Что проверить вручную»

**Unit-тесты — автоматически на PR.** Отдельный раздел только для того,
что тестами не покрывается: Vosk, TTS, UI, БД-миграции, реальное
устройство.

### 5.1. Режим А (AS, дома или на работе)

✅ Что проверить вручную — заход X.Y

Сборка

Ctrl+F9 → ожидаемо BUILD SUCCESSFUL.

Локальные тесты

Alt+F12 → ./gradlew testDebugUnitTest → BUILD SUCCESSFUL.

Device-check (если требуется)

Сценарий 1: <пошагово> → ожидаемое поведение.
Сценарий 2: ...

Если что-то падает

Куда смотреть (logcat, тег), что прислать (полный текст).

**Если device-check не нужен — писать прямо:** «Device-check — не нужен».

### 5.2. Режим Б / В (fallback)
✅ Что проверить вручную — пачка X.Y-bundle

Unit-тесты (авто)

На PR — job unit-tests (зелёный = можно мержить).

APK (если нужен device-check)

Повесить лейбл build-apk на PR → job build-apk → артефакт
app-debug внизу страницы запуска.

Device-check (если требуется)

Сценарий 1: <пошагово> → ожидаемое поведение.

Если что-то падает

Полный текст ошибки CI или logcat — в чат.

**Правила:**
- Команды в подсказке `>` — простые, по одной строке.
- Не дублировать то, что покрыто тестами.

## 6. Что делать при ошибках

### 6.1. Сборка упала
- Попросить **полный текст ошибки** (не скриншот).
- Найти причину, исправить, выдать **полный файл** заново.

### 6.2. Логика не работает
- Что происходит vs что ожидалось.
- Что нажал, что увидел, что в логах.

### 6.3. Миграция БД упала
- Снести приложение и запустить заново.
- Исправить `Migration`.

### 6.4. CI упал
- Попросить **полный лог** (не скриншот).
- Разобрать по шагам: `Setup Android SDK`, `Run unit tests`,
  `Build Debug APK`. Указать, где именно упало.

### 6.5. Юнит-тест упал
- Тест — это контракт. **Не удалять, не «подкручивать».**
- Сначала понять: тест прав или код прав.
- Если код сломан — откатить правку.
- Если тест устарел — обновить тест с пояснением в комментарии.

### 6.6. Git-конфликт
- Попросить имя ветки и имена файлов из конфликта.
- Объяснить пошагово, что оставить.

## 7. Правила по документации

### 7.1. Когда обновлять
- После каждого закрытого захода — `docs/PROGRESS.md`,
  `docs/NEXT_STEPS.md`, `docs/CONTEXT_BRIEF.md`.
- Решения — в `docs/DECISIONS.md`.
- Изменения БД — в `docs/DATABASE.md`.
- Изменения ГП — в `docs/VOICE.md`.
- Изменения правил работы — в `docs/AI_RULES.md`, `README.md`.
- Изменения тестов — в `docs/TESTING.md`.

### 7.2. Как обновлять
- Файл целиком, не фрагмент.
- Пометка «Заменить полностью» — жирным.
- Путь в текстовом блоке.
- Шапка `X/Y`.

### 7.3. Напоминание про репозиторий и коммит

**В самом конце ответа** — напоминание.

**Важно (§24):** merge в фичу и удаление пачки — **не в этом
сообщении.** Сначала пользователь прогоняет локально + device-check,
пишет «норм». Потом — отдельным сообщением git-шаги merge/delete.

**Для AS:**
Заход X.Y на проверке. Файлы можно пушить:

Репозиторий: https://github.com/ilia23star2-ops/GeoSampleManager

Ветка: fix/X.Y-bundle

Коммит: X.Y — краткое описание

**После подтверждения** — merge в feature/X.Y-xxx и удаление пачки.

**Для github.dev / github.com:**
Пачка X.Y-bundle на проверке. Файлы можно пушить:

Репозиторий: https://github.com/ilia23star2-ops/GeoSampleManager

Ветка: fix/X.Y-bundle

Коммиты:

X.Y-bundle/1 — Имя1

X.Y-bundle/2 — Имя2

**После подтверждения** — PR в feature/X.Y-xxx и удаление пачки.

**Unit-тесты запускаются автоматически на PR.** APK — по лейблу `build-apk`.

## 8. Принципы обсуждения

### 8.1. Перед кодом — обсуждение
Если задача сложная: сначала спецификация, потом код.

### 8.2. Не пиши код, если:
- Нет полного понимания задачи.
- Пользователь задал вопрос «как лучше?».
- Есть открытые вопросы по архитектуре.

### 8.3. Аудит
Перед крупным блоком — аудит: каталог команд, конфликты, вопросы.

## 9. Приоритеты

1. Работающий код > красивый.
2. Простое > сложное.
3. Понятный > лаконичный.
4. Документация > код без документации.

## 10. Что категорически нельзя

- Обрезать код («…», «остальное как было»).
- Угадывать содержимое файлов.
- Менять схему БД без миграции.
- Использовать Apache POI.
- Писать комментарии на английском.

## 20. Работа с двух машин

**Контекст:** проект разрабатывается на **двух машинах:**

- **Дома** — Android Studio, полный цикл.
- **На работе** — тоже Android Studio + git в терминале. Полный цикл.

**Fallback:** если AS недоступен — `github.dev` или `github.com`.

### 20.1. Модель веток — общая

**7 шагов git-цикла одинаковы для всех режимов.** Отличается только
интерфейс.
Подтянуть свежее из GitHub

Переключиться на фичу (или main для docs)

Создать пачку от фичи (или ветку от main)

Правки (и локальные тесты в AS)

Коммит + Push

Merge пачки в фичу (в AS — локально; fallback — PR)

Удалить пачку

**Правила:**
- **Пачка → в фичу**, не в `main`.
- **Docs → в фичу** (по умолчанию) или в `main`.
- **Фича → в `main`** — только когда вся серия готова.
- После merge **пачки** — удалить.
- После merge **фичи** — **не удалять** (архив, §2.9).
- **Подзаходы — отдельные ветки** `-1`, `-2`, `-3` (§2.8).

### 20.2. Режим А — Android Studio (дома или на работе)

**Главное:** git — **только через Terminal** (`Alt+F12`), не через
интерфейс AS. `AS Commit` ломает репо.

#### Шаг 1. Подтянуть свежее

Terminal:
git checkout feature/X.Y-xxx
git pull

**Ожидаемо:** `Already up to date.` или список обновлений.

#### Шаг 2. Создать пачку от фичи

Terminal:
git checkout -b fix/X.Y-bundle
git push -u origin fix/X.Y-bundle

**Проверка:** `git branch --show-current` → `fix/X.Y-bundle`.

#### Шаг 3. Правки и локальные тесты

1. Замени/создай файлы.
2. **Build → Make Project** (`Ctrl+F9`). Ожидаемо: `BUILD SUCCESSFUL`.
3. Terminal: `./gradlew testDebugUnitTest --no-daemon --max-workers=1`.
   Ожидаемо: `BUILD SUCCESSFUL`.
4. Device-check — если требуется.
5. **Дождаться «норм» от пользователя** (§24).

#### Шаг 4. Коммит + Push (после «норм»)

Terminal:
git add .
git commit -m "X.Y-bundle — <краткое>"
git push

#### Шаг 5. Merge пачки в фичу (локально)

Terminal:
git checkout feature/X.Y-xxx
git pull
git merge --no-ff fix/X.Y-bundle -m "Merge fix/X.Y-bundle"
git push

#### Шаг 6. Удалить пачку

Terminal:
git branch -d fix/X.Y-bundle
git push origin --delete fix/X.Y-bundle

#### Если PR фичи в main

PR делается **через github.com в браузере**. AS не умеет PR.

1. Открыть `https://github.com/ilia23star2-ops/GeoSampleManager`.
2. Вкладка **Pull requests** → **New pull request**.
3. **Base:** `main`. **Compare:** `feature/X.Y-xxx`.
4. **Create pull request**.
5. **Unit-тесты запустятся автоматически.**
6. Дождаться зелёного.
7. **Merge pull request → Confirm merge.**
8. **НЕ удалять** ветку фичи. Архив (§2.9).

### 20.3. Режим Б — на работе, `github.dev` (fallback)

1. Открыть репозиторий. Нажать `.` — `github.dev`.
2. **Переключиться на фичу:** внизу слева `main` → `feature/X.Y-xxx`.
3. **Создать пачку:** кнопка `main` → **Create new branch** от фичи.
4. Правки.
5. **Commit & Push** — Source Control (`Ctrl+Shift+G`).
6. **PR** — `Compare & pull request`. **Base: фича**.
7. **Unit-тесты — авто на PR.**
8. **APK** — повесить лейбл `build-apk`.
9. **Merge в фичу.** Пачку удалить.

### 20.4. Режим В — на работе, `github.com` (fallback)

1. **Переключиться на фичу:** `main ▾` → `feature/X.Y-xxx`.
2. **Создать пачку:** поле ввода → `fix/X.Y-bundle` → **Create branch**.
3. Правки по файлам, коммит под каждым: `X.Y-bundle/N — ИмяФайла.kt`.
4. **PR** — Compare & pull request → **base: фича**.
5. **Unit-тесты — авто на PR.**
6. **APK** — повесить лейбл `build-apk`.
7. Device-check.
8. **Merge в фичу.** Пачку удалить.

### 20.5. CI — что автоматически, что вручную

**Автоматически:**

## 23. Полные файлы, точечные правки

**Правило введено 25.09.2026.**

**Присылать — полный файл целиком.** Без «…», без «остальное как было».
Это железно (§2.5 п. 4, §10).

**Менять — только то, что требует задача.** Комментарии, форматирование,
пустые строки, порядок разделов — сохраняются как в исходнике.

**Почему так:**
1. Пользователь копирует файл одним движением: `Ctrl+A` → `Ctrl+V` → `Ctrl+S`.
   Обрывки копировать нельзя.
2. Пользователь сверяет diff — там должны быть только смысловые правки,
   а не удалённые комментарии и переставленные блоки.

**Как проверять себя перед отправкой:**
- Файл полный? Если есть «…» — не полный, доделать.
- Каждое изменение относится к задаче? Если нет — не трогать.
- Комментарии на месте? Если удалил — вернуть.

**Исключение:** если правок больше 30% — возможно, файл проще переписать
с нуля. Но и тогда комментарии и структура сохраняются.

## 24. Порядок закрытия захода

**Правило введено 02.10.2026.**

**Главное:** ИИ **не мержит пачку в фичу и не удаляет ветку**, пока
пользователь не написал явное **«норм»** после прогона тестов и
device-check.

### 24.1. Этапы

**1. ИИ выдаёт код + тесты** (полные файлы, git-шаги «создать ветку» →
«коммит в ветку пачки»).

**2. Пользователь:**
- прогоняет локально сборку (`Ctrl+F9`);
- прогоняет юнит-тесты (`./gradlew testDebugUnitTest`);
- прогоняет device-check из §5;
- **пишет «норм»** (или «работает», «ок», «+»).

**3. ИИ — только после «норм»:**
- даёт git-шаги **коммита** (если ещё не закоммичено);
- даёт git-шаги **merge пачки в фичу**;
- даёт git-шаги **удаления ветки пачки**;
- (для docs) даёт шаги **PR в main** и merge.

**4. ИИ обновляет доки** (`docs/PROGRESS.md`, `docs/NEXT_STEPS.md`,
`docs/CONTEXT_BRIEF.md`, `docs/TESTING.md`) — отдельной docs-пачкой.

### 24.2. Что значит «норм»

- **«норм»** = «проверил, всё работает, можно закрывать».
- **«не норм» / «упало» / «ошибка»** = ИИ разбирает, исправляет,
  выдаёт новые файлы. Возврат к этапу 1.
- **«пока не проверял»** = ИИ ждёт, ничего не делает.

### 24.3. Чего ИИ не делает

- Не даёт шаги merge/delete в том же сообщении, что и файлы кода.
- Не предлагает «а может сразу смержим».
- Не пишет «после проверки смержи» — это знание уже есть в §24.
- Не закрывает заход в `docs/PROGRESS.md` до «норм».

### 24.4. Почему так

1. Пользователь может найти проблему на device-check, которую
   юнит-тесты не ловят (Vosk, TTS, UI, реальная БД).
2. Откат смерженной пачки — дороже, чем откат ветки пачки.
3. Если пачка смержена в фичу до проверки, а потом откат —
   в истории фичи остаётся мусорный merge-коммит.

### 24.5. Исключение

**Docs-пачки (`.md`)** — можно мержить сразу. Сборка и device-check
для них не нужны.

**Разрешение пользователя «мержи сразу»** — можно. Но по умолчанию
жди «норм».
